## 2026-09-23 [decision] (spec) — capability set
Seven capabilities, each with intent + success:
CAP-1 Recruiter-grade first impression
CAP-2 Recruiter-mode forward-to-hiring-manager
CAP-3 Pattern library as organizing principle
CAP-4 Decentralized page-as-proof surface
CAP-5 Content editable without redeployment
CAP-6 Currently-building feed with stale-state fallback
CAP-7 Performance budget enforced

## 2026-09-23 [constraint] (spec) — locked
Vercel-hosted frontend + serverless functions; no always-on DB; static-first; additive content schema (Zod .partial + .passthrough); Lighthouse Perf ≥ 95 in CI; every page includes spine line + proof number + return path; pattern is a first-class content type with stable deep-link URLs.

## 2026-09-23 [decision] (spec) — Non-goals
No multi-user CMS dashboard. No blog/CMS pipeline. No analytics-driven personalization. No paid third-party services in critical rendering path. No bespoke backend (serverless functions only).

## 2026-09-23 [decision] (spec) — Success signal
A real recruiter who has never seen the site can visit, within 60 seconds, name what Sanjit builds, why it matters, and which case study they want forwarded to a hiring manager — and actually do the forwarding. Demonstrable via at least one real-world forward producing a hiring-manager reply within a week.

## 2026-09-23 [decision] (spec) — assumptions
A1: Single-author site; no need for multi-role CMS preview, role-based access, or collaborator workflows.
A2: Recruiter-mode is a deterministic client-side toggle (URL param or localStorage flag), not a behavior-derived prediction.
A3: Content is edited in a separate content repo; the deployed site reads it via on-demand ISR.
A4: The spine line ("He can do it — whatever you give him to build, he can build it for you, and better than others") is treated as fixed copy, not user-generated.
A5: Performance budgets (100KB homepage, 200KB any other route) are enforced in CI, not advisory.
A6: Lab tool demos are iframe-embedded from a sibling Lab host, not bundled into the main route's JS — keeps the homepage JS budget intact.
A7: Vercel KV is the canonical "live state" store for currently-building entries; the content repo remains the source of truth for static content.

## 2026-09-23 [question] (spec) — open questions
Q1: Forward-to-hiring-manager payload — single share URL, PDF export, or both? Affects CAP-2 success shape.
Q2: Currently-building source of truth — Vercel KV (phone-updateable without git push) or content-repo file (simpler, git-versioned)? Affects CAP-5 + CAP-6.
Q3: Recruiter-mode analytics — measure forward-button clicks (Plausible custom event) or keep it silent? Affects iteration on CAP-2 but adds observability surface.
Q4: Lab demos — iframe embed to lab.sanjit.dev sibling host, or fully independent Next.js routes under /lab/[slug]? Affects deploy topology and JS isolation.
Q5: i18n scope — Bengali support for any user-facing copy (per "2G Bangladesh mobile" constraint)? Affects font + content schema.
