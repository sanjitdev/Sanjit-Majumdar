Pattern · 01 · For multi-platform ERP integration

Canonical Model.

One normalized schema. Map at the boundary. Validate before write. Use it when 3+ systems need to agree on the same entity, and you can't replace any of them.

Used in
Wellbook (10K+ users)
Stack fit
.NET · SQL Server · REST
Team fit
3+ engineers, integration work
Risk if skipped
Schema drift, poison-pill queues
When to use

Apply this pattern when…

You have multiple systems (typically 3+) that each own a partial copy of the same entity, and you can't replace any of them.

Drift is already a problem. Translation tables are growing. The translation tables have translation tables. A vendor update in one system takes days to surface in another, and nobody trusts the reconciliation.

How to do it

Five moves.

  1. 1

    Define the canonical model

    One normalized representation that all sides can agree on. Pick the entity boundaries that survive every system. Don't let domain modeling leak into integration modeling.

  2. 2

    Map at the boundary

    Translate at the integration edge — never inside the domain. Each side speaks its own dialect; the boundary speaks canonical. If a domain layer starts translating, stop.

  3. 3

    Validate before write

    Reject inputs that violate invariants. Surface the why. Failed-closed with a clear reason is the difference between an integration and a queue of poison-pill messages nobody sees.

  4. 4

    Version the contract

    Schema changes ship with a migration. Never silently. Every consumer knows what version they're reading from and writing to.

  5. 5

    Make it replayable

    Source everything into an immutable log. Any state can be reconstructed from any window. This is what makes a forward-only migration safe.

When NOT to use it

Counter-lines.

Skip if · one system owns the truth

The others are read-only.

A direct projection from the source of truth is simpler, faster, and easier to reason about. Canonical Model is overhead you don't need.

Skip if · the schema fits on a postcard

You're translating fewer than five fields.

A mapper is enough. Canonical Model pays off when the entity graph has edges; for leaf fields it's ceremony.
