Canonical Model.

When N systems need one vocabulary, model it explicitly. Adapters translate. The canonical model becomes the only place that has to be right.

01 · When to use it

The integration is harder than the feature work.

You have two or more systems of record that need to talk about the same things. The vocabulary is already drifting. Reports require manual reconciliation. The team is spending more time translating between systems than building features.

If you only have one system, this pattern is overkill — a canonical model is one more thing to maintain. If the systems are read-only and the data is genuinely orthogonal, skip it.

02 · What it is

A stable vocabulary between N systems, owned by adapters.

A canonical model is an explicit schema for the shared entities (projects, vendors, finance events, documents) that two or more systems must agree on. It owns stable IDs, canonical fields, and the reconciliation rules when systems disagree.

The legacy systems stay. Each one gets an adapter — a scheduled job or event listener — that translates its native data into the canonical form and back when needed. The canonical layer becomes the only place where governance, audit trails, and cross-system reporting happen.

03 · How to do it · 4 numbered moves

The playbook.

01

Find the entities that need to be the same word

Start with the cross-system reports. The things finance, operations, and the regulator all reference. If three systems call a "project" something subtly different, that's your canonical entity. Map them.

02

Pick stable IDs and refuse to compromise on them

The canonical model needs IDs that survive every adapter round-trip. UUIDs work. Composite keys rarely do. Pick once, never change, document the rule.

03

Each system gets an adapter; adapters own translation, not policy

An adapter reads native data, maps it into canonical, and writes. It does not decide what the right answer is when systems disagree. Policy lives in the canonical layer or above it.

04

Make the disagreement visible — never silent

When two systems disagree on a governed field, both values should appear somewhere — one wins, one is logged as the deviation. Silent reconciliation is where audit trails die. We cannot ship a system whose truth isn't visible to its own operators.

04 · When NOT to use it

The honest counter-line.

When NOT to use it

When one system owns the truth and the others are read-only consumers, skip canonical model. You don't need a vocabulary if only one system is speaking. Point the consumers at the system of record and you're done — adapters for read-only views are cheap, but a canonical model is overhead with nothing to reconcile.

When N=1, skip it. The cost of maintaining a canonical schema is real. If you're not integrating, you're just paying it.

05 · Example

Where I applied it.

Real example · Case study CS · 01

Wellbook — three ERPs, one canonical schema

An oil & gas organisation had three ERPs from acquisitions. Each called a "project" something subtly different; reporting took three weeks of manual reconciliation.

We modelled projects, vendors, finance events, and document registers as canonical entities with stable UUIDs. Each ERP got an adapter. Each adapter mapped its native fields into the canonical model with explicit translation rules and reconciliation windows. Reporting went from three weeks to under an hour.

Tradeoff: three sets of credentials to manage, three audit logs to reconcile. Real operational overhead. The pattern earns its slot when the integration pain exceeds that overhead — it usually does.
