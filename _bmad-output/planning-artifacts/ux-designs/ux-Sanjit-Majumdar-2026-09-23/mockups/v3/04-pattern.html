Canonical Model

How to unify multiple systems of record under one authoritative schema — without rip-and-replace. This is the pattern I reach for when an organization has grown through acquisition, when consolidation is mandated, and when the existing systems can't be retired.

01 / When to use it

The shape of the problem this fits.

Reach for the canonical model pattern when two or more systems of record exist for the same business concept, when consolidation is mandated but rip-and-replace is not feasible, and when the people who run each system have legitimate reasons to keep running it.

That last clause is the one that gets skipped. If the people who own Finance's ERP, HR's HRIS, and Supply Chain's TMS all have sound reasons to keep their systems (regulatory, institutional knowledge, sunk cost, vendor lock-in), then a rip-and-replace is a 24-month political fight. The canonical model sidesteps that fight by giving each system owner what they want — autonomy over their system — while giving the business what it needs — a single view across them.

The pattern works less well when there is only one source system (just unify in place), when the source systems are unreliable (you'll be reconciling garbage), or when the business actually needs a true rip-and-replace for compliance reasons.

02 / What it is

An authoritative layer that owns the truth.

A canonical model is a schema, owned by your platform, that represents every business concept the organization needs to query across systems. Each source system has a read-only integration that streams its deltas into the canonical model. A normalization layer resolves conflicts. A write-back layer propagates agreed corrections back to source systems through explicit, audited sync jobs.

The canonical model is the only writable surface. Source systems are read-only from the platform's perspective. This is the hard rule that makes the pattern work — without it, you end up with two competing sources of truth instead of one.

From the user-facing application's perspective, the canonical model is the database. It doesn't know or care that there are three ERPs underneath. It reads, it writes, it gets conflicts surfaced for analyst review.

03 / How to do it

Four moves, in order.

01

Map the concepts before you map the schema.

Before writing any code, spend two weeks doing a concept-mapping workshop with one subject-matter expert from each source system. For each business concept (project, contract, vendor, employee), write down how each system represents it, what fields disagree, and which system's version is authoritative for which dimension. This document becomes your migration target.

02

Build the canonical schema to express the business, not any source system.

The canonical schema should not look like any of the source systems. It should look like the business. If your business thinks of a "project" as having one set of attributes, the canonical model has that set — not the union of attributes across three ERPs. The shim layer is where source-system attributes get mapped onto the canonical shape.

03

Run reconciliation on a schedule your business can absorb.

Nightly reconciliation is the right default for most regulated, mid-cadence businesses. Real-time CDC streams are the right answer only when the business genuinely needs sub-minute latency — and most don't. Auditable, predictable, lower-cost nightly jobs age better than always-on streams. Pick the cadence your stakeholders will actually trust.

04

Ship the read-only view before the write-back.

First deliverable: a read-only reconciliation view that lets analysts stop using Excel. Second deliverable: write-back for the most common correction types, gated by audit. Third deliverable: governance workflows (approvals, signoffs, audit trail). Each phase is a six-week cycle with regional pilots before global rollout. Don't ship write-back before read-only is trusted. Analysts will not trust write-back until they've validated read-only against their Excel for at least two quarters.

04 / When NOT to use it

The honest counter-cases.

When this pattern is the wrong call

If there's only one source system, just unify in place — the canonical layer is overhead with no payoff. If the source systems are unreliable, you'll spend your life reconciling garbage into the canonical model and propagating that garbage downstream. If the business genuinely needs a true rip-and-replace for regulatory or audit reasons, the canonical model becomes a halfway house that delays the inevitable and doubles the engineering work.

The pattern also fails when there's no executive sponsor with the authority to enforce the "canonical model is the only writable surface" rule. If each system owner can still write directly to their source without going through your platform, you have a data lake, not a canonical model. Make sure the sponsor can enforce the rule before committing.

05 / Example

Multi-platform ERP integration.

Worked example

A mid-cap energy operator with three legacy ERPs (one per region, acquired through M&A). Each ERP owns procurement, finance, and vendor master data for its region. The audit committee mandated consolidation in 18 months. Regional IT directors refused rip-and-replace — each ERP held critical regulatory knowledge for its jurisdiction. Solution: build the canonical model on .NET 5 + SQL Server, run nightly reconciliation jobs, ship a read-only analyst view first, then write-back for the most common contract corrections. Shipped in 14 months, two months ahead of the audit deadline.

Source systems
3 legacy ERPs, each with procurement, finance, vendor master
Canonical layer
SQL Server schema, normalized, single ID per business concept
Reconciliation
Nightly Azure Functions, conflict surface for analysts
