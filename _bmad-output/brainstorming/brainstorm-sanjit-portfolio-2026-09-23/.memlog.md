## 2026-09-23 [direction] (user) — constraint set
Hosting target: Vercel (frontend + light backend via Vercel-compatible services). Lightweight by design — show portfolio + a few tools. Static content with the option to extend with dynamic data later without restructuring. This means architecture must be: SSG-first, content-as-data (markdown/JSON), serverless-only dynamic pieces (no always-on DB), and content-schema should be additive — adding fields shouldn't break older entries.

## 2026-09-23 [idea] (coach) — First Principles, refactor
The CV four-vectors idea still holds, but the hosting constraint means each "case study card" is a *markdown file with frontmatter* loaded by SSG — not a CMS page. The four proof vectors become a typed content schema (vectors: scale, delivery, performance, leadership). Adding "Currently building" entries or new Lab tools becomes append-only frontmatter edits.

## 2026-09-23 [direction] (user) — strongest constraint yet
CV (and presumably other content) updatable any time without re-deployment. This means: content lives in a CMS / file source that the deployed site re-reads at runtime — NOT rebuilt on commit. So either (a) a headless CMS with on-demand ISR, or (b) a content source (file repo, Notion API, Sanity, etc.) the live site reads per-request. Either way, the *build* doesn't move when the *content* does.

## 2026-09-23 [idea] (coach) — architecture unlock
The cleanest version: content lives in a file structure the recruiter never sees but you edit locally. The deployed site reads it via a serverless function that returns the current state. No build pipeline runs on edit; a quick `git push` to the content repo (or a CMS save) flips a webhook → Vercel ISR regenerates *just that page*. Content schema is additive so old entries don't break. This makes "currently building" / "lab" / "case studies" truly alive without the cost of a real CMS dashboard.
